# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

grove is a terminal UI (Go, Bubble Tea v2) that shows every git worktree of a repository, the files each changed with +/- counts, a syntax-highlighted diff, and files changed in more than one worktree ("overlaps"). Module path: `github.com/azeem-yousaf/grove`. Primary platform is Windows; macOS and Linux are supported.

## Commands

```powershell
go build -o grove.exe .                      # local build
go install -ldflags "-s -w -X main.version=0.1.0-$(git rev-parse --short HEAD)" .   # install to %USERPROFILE%\go\bin
go vet ./...
gofmt -l .
go test ./... -count=1
go test ./internal/ui -run TestRemoveDialog -count=1    # single test
grove <repo> --plain                         # text summary; quickest end-to-end check of the git layer
grove <repo> --usage                         # tokens the agents used, by plan, task and agent
```

go.mod requires Go 1.26; an older installed Go downloads that toolchain automatically. The version shows in the header and `grove --version`. `-ldflags "-X main.version=…"` sets it; otherwise `buildVersion` uses Go's build info: the module version for `go install …@vX.Y.Z`, or `dev-<commit>` (with `-dirty` for uncommitted changes) for local builds.

Opt-in tests, skipped unless their environment variable is set:
- `GROVE_DEMO=<repo> GROVE_DUMP=<dir> go test ./internal/ui -run Dump` renders a real repository to `.txt`/`.ans` screen dumps for visual checks.
- `GROVE_SHOT=docs/screenshot.svg go test ./internal/ui -run ReadmeShot` regenerates the README screenshot. Rerun it after visible UI changes. The README uses an SVG because GitHub's code font lacks glyphs like ⚠ ● ■ ▾, which misaligns text screenshots.

## Architecture

`main.go` parses flags (they may come before or after the path), calls `git.Open`, then either prints `--plain` output or runs `ui.New` in a `tea.Program`.

### internal/git: everything goes through the real git CLI

- `run`/`runCodes` in `git.go` are the only way git is executed. They add `-C dir --no-pager -c core.quotepath=off -c color.ui=never` and set `GIT_OPTIONAL_LOCKS=0`, `GIT_TERMINAL_PROMPT=0` and `LC_ALL=C`. `GIT_OPTIONAL_LOCKS=0` matters: background scans must never take `index.lock` from the user's own git commands. Output is parsed from `-z` / porcelain formats.
- `Repo{Here, CommonDir, Name}`: `Here` is the worktree grove was launched from (it can be `""`, e.g. for a bare repo or after that worktree was removed). Commands that are not about a specific worktree use `CommonDir`. `Open` accepts a worktree, any subfolder or file, a `.git` folder, `.git/worktrees/<name>`, or a bare repo.
- `Scan` → `Snapshot`: `Worktrees` lists the worktrees, and `Inspect` runs for each one in parallel and produces a `State` (`State.Recent` is the newest five commits on HEAD from one `git log`; `Last` points at the first). `Snapshot.Overlaps` maps a repo-relative path to the indexes of the states that touch it.
- Modes: `ModeBranch` diffs against the merge-base with the base branch (`State.Rev`) and merges in `git status` (uncommitted and untracked files). `ModeUncommitted` diffs against `HEAD`. `FileChange.Uncommitted` marks files with working-tree edits in either mode.
- `DetectBase`: an explicit override wins; otherwise `origin/HEAD`, then `main`/`master`/`trunk`/`develop`, each local before `origin/`.
- Conflict prediction (`predict.go`, git ≥ 2.38, `[conflicts] predict` in config): `SideOf` turns a `State` into a `Side` (HEAD plus a tree; worktrees with uncommitted/untracked work get a tree from `Checkpoint`, so the real index is never touched). `PredictConflicts` makes throwaway `commit-tree` commits for unclean sides, runs `MergeConflicts`, and finds each side's clashing lines from `diff -U0` against the merge base (hunks whose base ranges overlap or touch). `Predictor.Predict` checks only pairs sharing a path in `Snapshot.Overlaps`, caches by (sorted trees, merge base), drops entries the last call didn't use, and returns nil on old git. `Cached` lets the merge review reuse a result. `--plain` prints a Conflicts section.
- Git policy (`internal/gitpolicy`, pure Go, no AI): `Classify(cmd, Bash|PowerShell, Scope, Lookup)` decides whether an agent's shell command may run on its own: `NotGit` (leave it to the normal approval flow), `Allow` (routine) or `User`, with a short `Reason`, `Protected`/`Destructive`/`Bypass` (could get around the git guard: hooks skipped or replaced, `-c`/`GIT_*`, `.git` written directly, an unguarded worktree or another repository) and the branches it changes (`Refs`). `policyOf` makes an approval `userOnly` only for a `User` verdict that is protected, destructive or a bypass; any other `User` command is the watching planner's to answer. `shell.go` parses the line like the shell would (separators, quotes, escapes including PowerShell's backtick and smart quotes, here-docs, `$( )`, backticks, subshells, script blocks), marking words whose value depends on the shell as `dynamic`; `$(cat <<'EOF' … EOF)` counts as a literal. `classify.go` walks the commands: `cd` is followed (pipelines and `&` don't move it), wrappers such as `command`/`env`/`nohup` are stripped, interpreters (`sh -c`, `xargs`, `eval`, `iex`, `pwsh -Command`, …) and substitutions that mention git, unsafe environment (`GIT_*`, `PATH`, `$env:GIT_DIR`), aliases/functions, writes into `.git`, and parse failures on a line that mentions git all give `User`. `gitcmd.go` holds one rule per subcommand (`gitRules`); `parseOpts` separates options from positionals with each command's value-taking options and resolves abbreviations. Branches come from `Lookup.CurrentBranch` of the folder git runs in (after `-C`/`cd`), or from an earlier `switch`/`checkout` in the same line (`moved`); protected names and globs match `x`, `heads/x` and `refs/heads/x` alike, ignoring case. Writes need the folder to be `Worktree` or one of `Writable`, and `Guarded`; read-only commands are also allowed in `Readable`. `GitLookup(ctx, dir)` answers through `git.CurrentBranch`, `AliasOf`, `RefExists` and `Pushed` (`lookup.go`; a same-named remote branch exists), caching per instance.
- `RemoveWorktree` handles the Windows case where git forgets the worktree but cannot delete a folder another process holds open (`FolderLeft`). It also `chdir`s out of the target, because child processes inherit grove's working directory.

### internal/ui: one Bubble Tea model

- All git work runs in `tea.Cmd`s and comes back as messages (`scanMsg`, `diffMsg`, `removeMsg`, `gitDoneMsg`, `actionMsg`). Stale results are dropped by sequence number: `scanSeq` for scans and `diffSeq` for the 60 ms diff debounce. Diffs are cached by `diffKey` (path + rev + file), and the cache is cleared on every scan.
- Refresh is polling, not file watching: every 3 s while focused, slower when the terminal is blurred, and immediately on `FocusMsg`. File watchers were avoided because a watched folder on Windows can block deleting it. While a removal is running (`m.removing`), `startScan` is a no-op; a removal requested during a scan is queued and started from `onScan`.
- `Update` runs `ensureCursorVisible` and `refreshDiffView` after every message. `refreshDiffView` re-renders the viewport only when its `renderedFor` cache key changes.
- The selection survives rescans through `selKey` (worktree path + NUL + file path) and `rebuildRows`/`findRow`, not by row index.
- Key routing order in `onKey`: quit confirmation → merge review (`m.conflicts`) → remove dialog (`m.confirm`) → new-worktree dialog (`m.creating`) → agent picker → who-watches question (`m.watchAsk`) → undo dialog → plan review → action palette (`m.actions`) → Ship menu (`m.ship`) → commit dialog (`m.commit`) → revert confirmation (`m.revert`) → diff search input (`m.searchActive`) → `:` git prompt → agent chat (`focusChat`) → help overlay → usage screen (`m.usageView`) → overview (`m.overview`) → filter input → global keys → pane-specific keys (`onListKey` / `onDiffKey`). Use `m.quit()` / `m.quitNow()` rather than `tea.Quit` so running agent processes are stopped. New modal states need a branch here, an overlay case in `render()`, and a matching footer case in `view.go`. Keys that mean something else in the diff pane (such as `n`, next hunk) belong in `onListKey`, not the global switch. A new action should also get an entry in `allActions` (`actions.go`, the `ctrl+k` palette), with a `when` that hides it where it doesn't apply; entries call the same methods as the keys.
- Token usage (`usage.go`): `m.usage` is the `usage.Ledger` in `<store>/usage` (nil without a store, as in `fakeModel`; tests set one with `withLedger`). Every session has a `uid` and a `turns` counter; `send` calls `startTurn` (turn ID `uid/n`, `turnAttr` noted with its `Kind` from `s.nextKind`, which callers set just before `send` through `sendAs`/`tellAs`, else work, or plan for the planner; `registerAgent` calls `SetAgent` on the first turn and when kind, model or branch change). `EvUsage` only updates `s.live`; `onAgentDone` calls `endTurn`, which queues exactly one `usage.Turn` in `s.unrecorded` with the attribution at that moment (`attrFor`: `taskFor`, else `mergedInto`; the planner keeps the plan chosen at the start, `s.nextPlan` from `orchestrate` or `watchingPlan`). The planner's turns without a plan collect in `s.drafting`, and `onPlannerReply` queues an `Assign` of them to the new draft in `s.unassigned` (the ledger keeps a turn's first assignment). Ledger writes never run in `Update`, since one may wait for another grove's lock: `flushUsage` writes a session's queued turns, then its assignments (never before their turns), in a `tea.Cmd`, one flush per session at a time (`s.writing`); `usageWrittenMsg` removes what was written, and the clock's `retryUsage` tries the rest again. Both queues are saved with the session; the ledger ignores turn IDs it has, so retries never count twice. `SetAgent` also runs in a command, and a failure clears `agentKey` so the next turn tries again. `endTurn` keeps `EvDone.SessionTotal` only from an Exact turn with a non-zero total, else clears it, as does a turn cut short. `forgetSession` records a running turn through `abandonTurn` and never removes usage. Figures show in the chat header (`agentUsage`), a group's summary, the overview's totals and plan lines, and the `T` screen (`usagePane`, `usageRows`, `usageCols`), which reloads the ledger when opened and every `usageReload` while open (`usageTick` from the clock); nothing else polls it.
- The footer (`footer` in `view.go`) shows as many hints as fit, then the `pinned` ones (`ctrl+k actions`, `? help`), which never get cut off.
- Desktop notifications (`alert.go`): `m.alert(text)` queues a line only while the terminal is blurred (`m.termFocused`, from `FocusMsg`/`BlurMsg`); alerts within `alertDelay` are flushed as one notification through `m.sendAlert` (`notify.Send`; tests stub it in `noAgents`), and dropped if the terminal regains focus first. Call it next to the toast for anything the user would come back for. After one failure `alertsBroken` stops further attempts. `internal/notify` has per-OS `Send`: a Windows toast via `powershell.exe -EncodedCommand` (text passed in environment variables, `CREATE_NO_WINDOW`), `osascript` on macOS, `notify-send` elsewhere, each run from the temp folder so it never holds a worktree open.
- `tea.PasteMsg` goes through `onPaste`, which follows the same order and drops pastes in dialogs without a text field. The chat input is a `textarea` (multi-line, `enter` sends, `shift+enter`/`ctrl+j` new line). Dragging over the chat, or a group chat (`chatSelection.group`, lines from `groupChat.lines`), selects whole lines and copies them on release (`chatselect.go`) because grove's mouse mode stops the terminal's own selection being useful.
- Plan groups in the list (`grouplist.go`): `rebuildRows` puts a `rowGroup` header (`row.wt` is -1) before the worktrees of each plan group (`findGroups`, via `taskFor`, for as long as the worktrees exist), at the place of its first member; members' rows carry `row.grp`, an index into `m.listGroups`. `selected()` skips group headers (they are neither worktree nor file); use `cursorRow()` when headers matter. Groups fold through `m.collapsed` under `groupKey(plan, group)`, which is also their `selKey`. `listLines` frames members in a box (`groupHeader` as the top edge, `groupSide`, `groupBottom`) at `groupBoxWidth` and wider, a left bar below it; the border colour comes from `groupStats`/`groupColor`. A selected header shows `groupSummaryLines` in the diff pane. `groupIcon` only uses a single code point two cells wide, else `⇄`; `splitGroupIcon` reads an emoji typed before the name in the plan review.
- The summary above the list (`dashboardPane`, `dashHeight`) takes rows from the list, so anything mapping screen rows to list lines (`listHeight`, `onClick`) must subtract `dashHeight()`. `w` shows `overviewPane` in place of both panes.
- Conflict prediction (`predict.go`): after each scan, when `cfg.Conflicts.Enabled()`, `startPredict` runs `m.predictor.Predict` (one run at a time, `predictSeq`, a second request sets `repredict`; never while `m.removing`). `onPredict` applies results only if their snapshot is still `m.snap`, then calls `onConflictsChanged(prev, next)` (`conflictnotify.go`). `onScan` remaps the old `m.predictions` onto the new snapshot by worktree path, so `Prediction.A/B` always index `m.snap.States`. `conflictsFor`/`willConflict`/`conflictLines` answer per file: ✗ (`st.conflict`) marks files that will conflict, ⚠ those that overlap but merge cleanly or aren't known yet. `o` cycles `overlapView` off → overlaps → conflicts → off (skipping conflicts when there are none). The diff pane's hunks whose changed lines meet `conflictLines` get a `┃` gutter bar and a tinted header (`clashingHunks`); the ranges are in `renderedFor`. If git is older than 2.38 a toast says so once and only ⚠ shows. The merge review asks `m.predictor.Cached` before `mergeConflicts`.
- The merge review (`conflicts.go`, `c`) keeps worktrees by path and branch, never snapshot index, since scans continue while it is open. Stages: check each branch (`git.CommitsBetween` + `git.MergeConflicts`) → choose → preview in order (`git.PreviewMerges`, throwaway commits via `commit-tree`) → merge (`git.Merge`, which detects conflicts from unmerged paths, not git's output) → conflict screen (ask agent / editor / `git merge --abort`).
- Overlays (help, remove confirmation) are composited over the screen in `render()` and clipped to the terminal. Layout switches to one pane at a time below 100 columns, and the minimum size is 50×12.
- `:` (`gitcmd.go`) runs git through `tea.Exec` with a custom `ExecCommand` (`gitRun`). Git gets the real terminal, so editors, pagers and prompts work. `gitRun` waits for Enter before grove redraws. `runSteps` runs several `termStep`s in one handover, stopping at the first failure; its `after(ok)` callback learns the outcome.
- Reviewing (`wtdiff.go`): `v` sets `m.wtView`, which `refreshDiffView` renders in place of the summary or file diff from `git.WorktreeDiff` (one `git diff <Rev>` plus each untracked file, in `State.Files` order) or, after a second `v`, `git.DiffSince(session.turnTree)`. `send` takes a checkpoint before every turn for `turnTree` (saved with the session; unpinned, so dropped on load if gc took it). The view reloads when `wtKey` (a fingerprint of the worktree's files) changes, and closes whenever the diff pane loses focus (in `Update`). `parseDiffs` with `files` adds a `lineFile` line per file; every `diffLine` carries `hunk`, an index into `parsedDiff.hunks` from `git.ParseHunks`. `m.curHunk` is the hunk `x` (`git.RevertHunk`, which edits the file itself to keep CRLF, asked through `m.revert`) and `>` (quotes it into `m.chatDraft`, which `showChat` puts in the input) act on; `currentHunkIndex` falls back to the first hunk on screen, and `diffGutter` draws a bar beside it. `/` in the diff pane searches (`m.searchQuery`, lower case) instead of filtering; `renderDiff` highlights the first match per line with `searchBg`, and `n`/`N` follow matches while a search is set.
- Ship (`ship.go`, `s`): `openShip` loads `git.UpstreamOf`, `MergeInProgress`/`MergeMessage` and `git.RemoteBranch` for the base in a `tea.Cmd` (`shipLoadedMsg`); `shipItems` turns that plus the scan into the menu lines, each with why it can't run. Commit, push, `gh pr create` and merge/rebase from base all go through `runSteps`. The commit dialog (`commitDialog`) commits through `git.PlanCommit`: literal pathspecs in temporary files, `add --all` for paths on disk, `rm --cached --ignore-unmatch` for paths gone from disk (deleted, or the old name of a staged rename), then `commit -- paths` (a whole commit during a merge). Its message comes from the agent's last suggested `git commit` (`commitMessageOf`), else the task title. Pull requests come from `gh pr list` (`internal/gh`) via `m.listPRs` (stubbed in `noAgents`), at most once a minute while focused (`pollPRs`), keyed by branch in `m.prs`; a failure sets `prOff` and `prErr` until the next forced poll.
- Every colour comes from `theme.go` (`palette` / `styles`), with separate dark and light sets. `fill()` re-applies a row's background after each ANSI reset so styled segments don't punch holes in highlighted rows. Diff syntax highlighting uses Chroma (`catppuccin-mocha` / `github`).

### internal/agent and the per-worktree agents

- `agent.Runner.Run` drives an installed CLI for one turn and turns its JSON-lines output into `Event`s, ending with exactly one `EvDone`. Claude: `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --permission-mode acceptEdits --allowedTools …`, kept running per worktree (`claudeProc`) and sent one JSON user message per turn; a turn ends at its `result` line, not at process exit. Startup (hooks, plugins, MCP servers) takes seconds, which is why the process is kept and `Warm` starts it when the chat opens. A turn whose model, allow rules or session differ from the kept process's gets a new one with `--resume <session_id>` (this is what approving a command does). Stopping sends an `interrupt` control request, which keeps the process usable; it is killed only if that is ignored. Idle processes end after `Runner.Idle`; `Stop` ends one and waits, which removal needs because Windows can't delete a folder a process is using. `--allowedTools` is variadic, so it must stay last. Refused tools arrive in the result's `permission_denials`, unless a `PermissionRequest` hook (e.g. GitKraken's) holds the turn waiting for its own answer. Codex: `codex exec --json --sandbox workspace-write -`. Each turn is a fresh run with the conversation replayed in the prompt, deliberately avoiding `codex exec resume`. `Runner.Replay` caps what is replayed (`DefaultReplay`): the newest `Full` turns whole, older ones with the reply cut to `Brief` characters, within `Budget` characters, and one line for the turns left out; the briefing and the message are never cut, and the UI's `session.history` stays complete. Everything long (briefing, history, message) goes through stdin, never the command line. On Windows, `Find` prefers `name.exe` over npm `.cmd` shims.
- Token usage (`tokens.go`, types in `internal/usage`): `EvUsage` carries the turn's usage so far (a running total, sent when it changes), and `EvDone` its `Tokens` and `TokenStatus`: `Exact` (the provider's figure, also after an error or interrupt), `Partial` (cut short, live figures only) or `Unknown` (nothing usable; never estimated, never a fake zero). `Input` always includes cached tokens. Claude, checked against the real CLI (Haiku, one kept process, a Task subagent, a `--resume` restart): the `result` line's `usage` is the turn's own but leaves out subagents; `modelUsage` (per model, subagents included) and `total_cost_usd` add up over the whole session and carry on after `--resume` (so `Cost` is the session's total). The turn's figure is therefore the `modelUsage` sum minus the session's total before the turn: zero for a new session, else `Runner.totals` (by session id, from each `EvDone.SessionTotal`), else `Request.SessionTotal`, which the UI saves to survive a grove restart. With no base, or one that doesn't fit (`covers`: nothing may go down or end below `result.usage`, e.g. after the session was used outside grove), it falls back to `result.usage` as `Partial`. A turn that ends without a total (killed, or no usable `modelUsage`) still added to the session in Claude Code, so `noteTotal` marks the session's total unknown (nil in `Runner.totals`), which also overrides a stale `Request.SessionTotal`; the UI clears its saved total then too. Anthropic's `input_tokens` excludes the cache, so `Input` adds `cache_creation_input_tokens` and `cache_read_input_tokens`; `output_tokens` includes thinking. Live figures come from `message_start` (input side) and `message_delta` (usage so far, no message id: it belongs to the last `message_start`), summed by message id; `assistant` lines repeat their message's usage per content block and are never counted. Subagents stream no events, so live figures leave them out. Codex (checked with a real `codex exec --json` turn): `turn.completed` (or `turn.failed`) `usage` only, no live figures; OpenAI's `input_tokens` includes `cached_input_tokens` (and, assumed since it was 0, `cache_write_input_tokens`), and `output_tokens` includes `reasoning_output_tokens`, so none is added again; several turns in one run are added up.
- The UI keeps one `session` per worktree path (`m.sessions`, looked up with `sessionFor`, which uses `SamePath`). `send` runs the agent in a goroutine, which first takes a checkpoint if the session has none, and feeds `agentMsg`s through a channel that `listen` re-arms after each message. Claude denials become approval cards (`pending`); approving adds `agent.ClaudeRule(cmd)` to `session.allow` and resumes. Fenced `grove-run` blocks in replies become suggested-command cards. `agent.EvOutput` (Claude's `tool_result` for a Bash/PowerShell `tool_use`, Codex's finished `command_execution`) carries the end of a shell command's output; the chat shows it as a `roleOutput` entry (pass/fail line plus the last `testOutputLines`) only for commands `isTestCommand` recognises. The merged plan's own test runs show the same way in the planner's chat and post their output tail in the plan chat. Replies are rendered by `renderChatText`: prose gets its Markdown (code spans, bold, italics, links, list bullets and task boxes with hanging indents, headings, quotes) applied without the marks (`markdown.go`); tables are laid out in columns that wrap between words, with a rule between rows once a cell wraps, and become "header: value" lines when a word would have to split (`table.go`); code blocks keep their lines, and a line too long for the pane wraps onto lines that start with `↪` (`codeLines`), which `selectedChatText` joins back when copying.
- `Request.Env` is added to the agent process's environment (e.g. the git guard's `GIT_CONFIG_*`); `Request.Hook` is the `grove agent-hook` command line, which Claude gets as a PreToolUse hook on `Bash|PowerShell` through `--settings` (`hookSettings`, quoted for sh/Git Bash by `shellCommand`, 30 s timeout). Both are part of what a kept Claude process was started with, so a change restarts it with `--resume`. Codex gets `Env` but has no hooks.
- Agent hook (`internal/agenthook`): grove's UI writes each agent's `gitpolicy.Scope` to `<store>/control/policy.json` (`WritePolicy`, `Policy.Set`, keyed by `git.PathKey(worktree)`) and approved commands to `grants.json` (`AddGrant`, one use each, expire after `GrantTTL`, under `grants.lock`). `grove agent-hook --dir <control> --as <worktree>` (`Hook.Run`) reads Claude Code's PreToolUse JSON from stdin: a matching grant (`TakeGrant`, whitespace-normalised) → `allow`; else `gitpolicy.Classify` with `gitpolicy.GitLookup`: `NotGit` → no output (Claude's own permissions apply), `Allow` → `allow`, `User` → `ask`, which in `-p` mode becomes a permission denial and so an approval card. No policy, a damaged one, an unknown worktree or unreadable input asks for git commands (fail closed).
- `git.Checkpoint` writes the worktree into a tree object through a temporary `GIT_INDEX_FILE`, with `--attr-source=<empty tree>` and `core.autocrlf=false` so blobs are exact bytes. `RestoreCheckpoint` writes blobs back with `cat-file`, not `git restore`, which would re-apply CRLF conversion.
- Tests replace `m.installed`, `m.runAgent`, `m.warmAgent`, `m.stopAgent` and `m.saveAgent` (see `noAgents` and `fakeAgent`). In `internal/agent`, the test binary doubles as a fake Claude that speaks the stream-json protocol (`fakeClaude`); a fake that reads stdin to EOF before answering hangs, because the kept process's stdin stays open. `noAgents` also clears `m.opener.Editor`; otherwise tests that run the create flow launch VS Code for real. `pump` in `agent_test.go` runs commands concurrently and feeds agent and undo messages back into the model.

### internal/store and internal/plan

- `store.Store` keeps grove's own state as JSON under `<CommonDir>/grove` (shared by every worktree, never committed). `Save`/`Write` replace files atomically (temp file + rename). `Model.store` is nil when the repo has no common dir, which is the case in `fakeModel` tests, so those never touch disk.
- Agent sessions are saved per worktree as `sessions/<git.PathKey(path)>.json` (`persist.go`). The clock calls `persistSessions` every second, which writes only sessions (and plans) whose JSON changed since `savedJSON`, which records a file only once its write succeeded; `quit`/`quitNow` call `persistNow`. `loadSessions` runs from `Init`, drops sessions whose folder is gone, and clears checkpoints git no longer has. A session saved while running is restored with a "cut short" note. Removing a worktree calls `forgetSession`. Version 2 adds token usage: `uid`, `turns`, the planner's `drafting` turns, Claude's `session_total` (passed back as `Request.SessionTotal`, cleared when the session ID changes), and `running_turn` (the running turn's ID, attribution and live figures) while a turn runs; `onSessionsLoaded` records that turn as Partial (Unknown without figures) through `recordCutShort` and leaves `savedJSON` unset so the file is rewritten without it. The ledger ignores a turn ID it already has. Version 1 sessions get a new `uid`.
- Token usage (`internal/usage`, provider-independent: no imports from `agent` or `ui`) is kept in `<store>/usage/ledger.jsonl`, an append-only JSON-lines file that is never rewritten or truncated, so history outlives restarts, removed worktrees and finished plans. Each line has `"v":1` and one of `agent` (`AgentInfo`: grove's own id per agent conversation, never the provider's session id; appended by `SetAgent` only when it changed), `turn` (`Turn`: `Tokens`, `Status` Exact/Partial/Unknown, plan/task/group) or `assign` (`Assignment`: gives turns with no plan, such as the planner's drafting turns, to a plan; the first assignment wins and a turn's own plan is never moved). Appends happen under `internal/fslock` (`<dir>/lock`) after catching up with other processes' lines, and start on a new line if a crash left the last one unfinished. `Reload` reads only past the last offset (a stat when nothing changed) and leaves a line without its newline for later. Malformed lines and negative counts are skipped and counted (`Skipped`); duplicate turn IDs count once. A turn's optional `kind` says why it ran (`work`, `resume`, `wake`, `decide`, `plan`, `fix`; lines without one count as `unknown`), totalled by `ByKind` and shown as "By kind" with each kind's `Share` on the `T` screen and in `--usage`. Queries (`Total`, `Agent`, `Plan`, `Group`, `Task`, `Planner`, `PlannerIn`, `Unassigned`, `Agents`, `Plans`, `Groups`, `Tasks`) come from running totals kept under a mutex. A `Sum` that isn't `Complete` is a lower bound: the shared formatters (`Compact`, `Amount`, `Cached`, `Shortfall`, `FormatSum` in `format.go`) show its total as `≥N`, and turns that reported nothing as `?`, never 0. `grove --usage [repo]` (`printUsage` in `main.go`) prints the ledger by plan, group, task and agent.
- Checkpoints are pinned with `refs/grove/checkpoints/<PathKey>` (`git.KeepCheckpoint`) so `git gc` can't delete them before undo; `DropCheckpoint` removes the ref.
- The planner (`planner.go`, `review.go`, key `P`) is a `session` with `planner: true`, kept in `m.planner`, not `m.sessions` (it runs in the main worktree, whose own agent keeps its slot). `allSessions()` includes it; `agentMsg.planner` routes its events; `chatPlanner` makes the chat pane show it. Its requests set `agent.Request.ReadOnly`: Claude gets `--permission-mode default`, `--disallowedTools` for the edit tools and the read-only Atlassian tools allowed; Codex gets `--sandbox read-only`; `procKey` keeps its Claude process separate from the folder's worktree agent. A reply with a grove-plan block becomes the draft plan (one at a time) and opens `planReview`, which edits a copy. Starting (`s`) runs `checkPlan` (branches and folders) then `startPlan`; `schedule` starts queued tasks while `busyTasks` < `cfg.Planner.Slots()`, called after scans, task creation and task turns. `onTaskTurn` marks a task finished when its agent's turn ends without pending cards or a closing question; `taskContext` adds the task to the agent's briefing. Plans are saved through `changedSessions` with the sessions.
- Group chats (`internal/group`, `groupchat.go`): each plan group is a folder `<store>/groups/<plan>-<group>` with `messages.jsonl` (appends guarded by a `lock` file, since agents' tool servers write from other processes), `members.json` (written by `writeGroupInfo` on every `savePlan`) and a `read-<member>` cursor per member. `grove mcp-group --dir … --as <branch>` (`main.go`, `group.Serve`) is a minimal stdio MCP server with `members`/`post`/`read`; `groupTools` passes it to grouped tasks' agents only (`agent.ToolServer` → Claude `--mcp-config` plus `mcp__grove__*` allow rules, Codex `-c mcp_servers.grove.*`). The clock polls groups every second (`pollGroups`, guarded by `pollingGroups`); `wakeGroups` starts a turn for idle members with unread messages, once the chat has been quiet for `cfg.Planner.SettleDelay()` (`groupState.newest`, when a poll last saw new messages) or the member's messages have waited `config.SettleMax` (`groupState.since`), until `cfg.Planner.Wakeups()` in a row (wakes for grove's messages alone, `groupState.from`, don't count; a finished or failed task, `taskDone`, is woken only for messages addressed to it or the user's posts, and gets conflict news as `notes`), and `postToGroup` (the user, `focusGroup` pane, key `t`) resets the count. Every started plan also has a plan chat, group ID `plan.ChatID` (`Chat`, `Chats`, `ChatMembers` include it; `Tidy` renames a planned group that took the ID): every task's agent gets it as a second tool server named `plan`, but is woken only for messages addressed to it (`groupState.direct`); anything the user posts there wakes the watching planner. `t` on an isolated task or a plan's merge worktree opens it, `ctrl+t` switches between a group's chat and its plan chat, and `ctrl+g` in the planner's chat opens the latest plan's. Grouped agents also get `Request.ReadDirs` (`groupmateDirs`): Claude allow rules from `agent.ReadRule` (`Read(//path/**)`, Windows paths as `//c/...`) so they can read, but not edit, groupmates' worktrees; `agentContext` lists groupmates as readable instead of off limits.
- Orchestrator (`orchestrate.go`): before planning, `askWatcher` asks who watches the next plan (`[planner] watcher` answers it; the answer is `m.planWatch` until `startPlan` clears it) and `onPlannerReply` copies it to `plan.Orchestrated`; `o` in the review switches it. For a watched plan, `queueTurn` (from `onTaskTurn`: refused commands, or a closing question) and `queueGroups` (from `onGroupsRead`: new group messages, history skipped through `orch.seen`) queue `orchItem`s; `orchestrate` sends the planner one turn for the queue when an item is `urgent`, the planner is free and the items have settled (`itemsSettled`: no urgent item for `cfg.Planner.PlannerSettle()` after `orchItem.at`, the oldest waited `config.SettleMax`, or an item is `now`: a user post, or an agent that also waits on a userOnly card; the clock calls `orchestrate` while the queue isn't empty) (creating the planner if needed), and shows a one-line note in its chat in place of the request. `applyDecisions` carries out the reply's last grove-orchestrate block (approve/deny pending approvals by `id`, else branch and command, reply to a task's agent through `tell`, post in a group or the plan chat `From: group.Planner`), touching only watched plans. `decide` returns an `outcome` per decision (`control.Applied`, `AlreadyApplied`, `NotFound`, `NeedsUser`, `Failed`); a block's decisions that didn't apply get a note in the planner's chat and a line in its next request (`orch.reports`). Approvals (`approvals.go`): every approval `pendingAction` has an `id` (`nextApprovalID`: the worktree's `PathKey` prefix plus `session.seq`, saved) and an `approvalPolicy` from `m.classify` (a stub until gitpolicy lands; `userOnly` means only the user may answer, shown on the card as "needs you: <reason>"). Matching is by ID, else `control.NormCommand` (whitespace, quotes, escaped backticks). Every answer goes through `answer` (by user or planner): Claude rule plus `m.grant` (the agent hook's one-time grant; stubbed), a note in the agent's and the planner's chat, a line in `<store>/approvals.jsonl` (`control.LogActivity`), and `session.answered` so a repeat is "already applied". The planner can't approve a `userOnly` item (`refuse`: stays for the user, toast and alert). `resume` carries the agent on: after the planner's answers as soon as nothing is left for the planner (`awaitsPlanner`), telling it what was approved, denied and still waits for the user; after the user's once every card is answered (the original manual flow); answers given while it works go with the end of its turn. When the planner's turn ends, `leaveUndecided` deals with the approvals it was asked about (`orch.asked`) and didn't answer: one it may answer is asked again (`pendingAction.asked`, a line in `orch.reports`) and after `askAgain` turns denied for it so the agent goes on; only ones it may not answer are marked `left` for the user, with an alert. On a watched plan the planner is in charge: its agents' and its own finished turns only toast (no desktop alert) unless something is `userOnly`, and a planner denial doesn't alert. `userActed` (chat send, card answer, group post) and `progressed` (a watched task finished, merged tests passed) reset the `cfg.Planner.Decisions()` limit, so it only stops a planner going round in circles. When a watched plan's group reaches the wake-up limit, `wakeGroups` queues an urgent `orchGroup` item asking the planner to settle it instead of waiting for the user; a `plannerPost` resets the group's wake-ups. `queueTurn` also queues `orchFinished` and `orchFailed`, so the planner checks finished work; a `reply` reopens a finished or failed task and `mark` sets one finished or failed. `orchFinished` goes through `checkFinished` (HEAD read in a command, `finishedHeadMsg`): a task that was already finished and reports finished again at the HEAD it was last checked at (`session.finishedHead`, saved) isn't queued again. A working task whose turn ends without finishing or asking (e.g. only command cards wait) queues a non-urgent `orchIdle`, which goes with its owner's next turn or is made urgent by the clock's `idleTick` after `idleWait` (2 min). The decision rules (`orchRules`: block format, control tools, approval rules) are sent in full only when `rulesFor` says the planner's conversation lacks them (no session ID, Codex, or a different `rulesKey` from `session.rulesSent`, which is saved and cleared when the session ID changes or a turn fails); otherwise the request ends with one short line. `applyDecisions` parses the block and hands it to `decide`, which the control tools use too.
- Group planners (`crew.go`): every group of a watched plan has its own planner, a planner `session` with `crewPlan`/`crewGroup` (`crewKey`), kept in `m.crews` (in `allSessions`), saved under `crewDir`, briefed by `crewContext`, and run in the planner's folder with its own Claude process (`agent.Request.Slot`, part of `procKey`). `orchestrate` groups the queue by owner (`ownerOf`: a grouped task's approvals, questions, finished and failed news and its group chat go to that group's planner; ungrouped tasks, the plan chat, settling, merging and reviews to the lead) and `orchestrateOne` starts each free owner's turn, creating it through `plannerFor`. Each planner has a `plannerState` (turns, paused, asked, reports): the lead's is embedded in `m.orch`, a group planner's is `session.crew`; `stateOf` picks it. `applyDecisions(s, …)` runs a group planner's block through `scopeDecisions` (its group's tasks only, posts to its group chat unless it names the plan chat, no merge or close) before `decide(by, …)`; `ownerPlanner(path)` gets notes about a task's approvals. The user opens one with `P` on its group in the list or `ctrl+p` in its group chat (`openCrew`); `ctrl+g` in its chat opens the group chat. A user's post in any chat of a watched plan wakes the planner that owns it.
- Side turns (`side.go`): while an owner's planner is running, `orchestrateOne` hands its urgent `orchApproval`/`orchQuestion` items to `sideTurn` (everything else keeps waiting): a planner `session` with `side` set, one per owner in `m.sides` (`sideKey`, also its `Slot`), forked from the owner's `s.id` (`agent.Request.Fork`: Claude `--resume <id> --fork-session` in a process that ends with the turn; Codex ignores it), with its own `uid` and plan/group attribution, counted in the owner's `turns`. None before the owner has a session ID. Its block goes through `applyDecisions`/`scopeDecisions` (no merge or close, no control tools), `noteTo` writes to the owner's chat (`sideOf`), and applied decisions go to the owner's `plannerState.whileBusy`, which `orchPrompt` reports in its next request. It is saved under `sideDir` without its chat, for its usage only.
- Merging a plan (`planmerge.go`): a watched plan whose tasks are all settled stays `Running`; `finishIfSettled` queues `orchSettled` instead of marking it done, and the planner asks for the merge (`merge` in the block, or the `merge` control tool). `mergePlan` (refused with a reason from `mergeBlocker`, passed back as `orchMerge`) makes the plan's own worktree on first use (`plan.Merge`, branch `plan/<slug of title>` from `p.Base`, `freeBranch` avoids taken names and folders, `[new] copy` files copied in), commits each finished task's worktree with `git.CommitWork` (its suggested commit message, else the title; copied files excluded), and merges the branches in plan order with `git.Merge`. A conflict is aborted; grove merges the plan branch into that task's worktree and `tell`s its agent to resolve the markers (`Merge.Fixing`, task back to `Working`); `fixTurnEnded` (from `onTaskTurn`) runs `git.ConcludeMerge` when it says it's done, which commits the merge or lists files still holding markers, then merges the plan again. A clean merge sets `plan.Review` and posts in the plan chat `From: group.Grove` (`grovePost`; the planner never gets grove's plan chat posts relayed). With a test command (`testCommand`: `[planner] test`, else `plan.Test` from the grove-plan block) `runPlanTests` runs it in the merge worktree through `internal/shell` (sh / cmd.exe, `CI=true`, process tree killed at `TestTimeout`), tracked in `m.testingPlan`; `onTestsDone` records `Merge.Tests` and queues `orchMerge` either with `reviewAsk` (passed: summarise in the plan chat and wait for feedback, plus `waitForFeedback`'s toast and alert) or with the output tail and `testFixAsk` (failed: send failures to the responsible tasks' agents and merge again, ask the user only as a last resort; no alert). Without a test command the planner is asked to test it itself; a `reply` reopens a task (plan back to `Running`) and merging again brings in the new commits; `close` (`closePlan`) sets `Done`. `mergedInto(path)` finds the plan a worktree is the merge of. Unwatched plans still become `Done` and leave merging to the user.
- Planner control (`control.go`, `internal/control`): while a watched plan is `Running` or `Review` (`orchestrating`), the planner's requests set `agent.Request.Commands` (Claude: `Bash`/`PowerShell` allowed, edit tools still disallowed; Codex: `workspace-write`) and get `grove mcp-plan --dir <store>/control` (`controlTools`). Every second `pollControl` writes `control/state.json` (watched tasks, busy agents, approval cards, reply tails) when it changed and takes the tool server's queued `orders.jsonl` (`control.Take`, under an `internal/fslock` lock); `onControl` turns them into `decisions` for `decide` and records each order's outcome under its ID in `control/results.jsonl` (`control.Record`, last 200 kept); an order ID seen before (`orch.orders`) is "already applied". Tools: `tasks`, `message`, `approve`, `deny`, `mark`, `post` (plan chat by default), `merge`, `close`; plan-wide ones take a plan ID or title, optional when only one is running. state.json and `tasks` list each approval's `id`, command, reason and whether the planner may answer it; `approve`/`deny` take an `id` (the task is then optional) or a command. The tool server validates orders against state.json before queueing; `approve`, `deny` and `message` then wait up to `control.Wait` (5 s) for grove's result and return it, or say it is still pending. Both tool servers (`mcp-group`, `mcp-plan`) are built on `internal/mcp`.
- Conflict news (`conflictnotify.go`): `onConflictsChanged(prev, next)` runs after each conflict prediction (indexes into `m.snap.States`) and tells task agents when their worktree starts conflicting with another, or the set of files grows. `m.conflictsTold` (keyed by own path + NUL + other path) stops repeats and forgets pairs that stop conflicting; a pair whose prediction failed (`Err`) keeps its entry. Grouped tasks get a group message `From: group.Grove` `To` their branch (the resulting `groupPostedMsg` poll wakes them, counting as a wake-up); others get `session.notes` (saved with the session), which `takeNotes` in `send` puts in the briefing on a first turn and ahead of the message after that. Worktrees without a task, and the planner, are never told.
- Sticky approvals (`sticky.go`, `approvals.go`): task agents get the plan's test command as allow rules (`planChecks`: `agent.ClaudePrefixRule` per command, e.g. `Bash(go test:*)`, else the exact one, nothing for git), and an approval with `"prefix": true` adds the command's family rule (`familyRule`; git, interpreters, `go run`-like subcommands and chains get the exact one); neither applies to the planner's own session. Each approval also remembers the worktree (`worktreeMark`: HEAD and a fingerprint of the scan's changed files, saved; the first scan started after the card was made takes it again, `markApprovals`); one whose worktree moved on since is shown to the planner with "(worktree changed since it was asked)" in its request, state.json (`Approval.Stale`) and the `tasks` tool, and is never denied for that.
- Git autonomy (`gitauto.go`, state in `m.auto`): agents commit and integrate their own work; protected branches (`protectedBranches`: main, master, the base branch without its `origin/`, and `[git] protected` names or globs) change only with the user. The clock's `gitAutoTick` installs the guard (`gitguard.Install` into `<store>/hooks`) whenever the protected list changes, which bumps `m.auto.gen`; `verifyGuards` runs `gitguard.Verify` in every agent's worktree (`agentDirs`: sessions, started plans' task and merge worktrees) not checked since; `send` checks a new worktree first and waits for the result (`agentMsg.guard`/`ack`). `guardStatus`/`guardBadge` show "🛡 guarded" or "unguarded: git writes need you" in the chat header, the overview's AGENT column and its attention list. `writePolicy` writes every agent's `gitpolicy.Scope` to `control/policy.json` (`agenthook.WritePolicy`) only when its JSON changed: worktree, branch from the scan, groupmates readable, protected, guarded. The planner's key is `plannerAs()` (`<control>/planner`), since it shares the main worktree with that worktree's agent: `Dir` the main worktree, readable; its watched plans' task and merge worktrees writable. `agentRequest` sets `Env` = `guard.Env()` for every agent and `Hook` = `grove agent-hook --dir <control> --as <hookAs>` for Claude. grove-run lines go through `suggestedLines`: a plain git line (`plainGit`: no shell characters) that `gitpolicy.Classify` allows is run by grove (`git.Exec`, no shell, guard env, `gitTimeout`) in the background, shown in the chat and sent to the agent (`onAutoGit`; into `notes` while cards wait); anything else, and every line after one that needs the user, becomes a card with `policy`. `runKey` (session, turn start, line) keeps a line from running twice; `gitBusy` keeps the task from counting as finished meanwhile. `m.classify`/`m.grant` are `gitClassify`/`gitGrant`: an `agenthook.AddGrant` for every approval, plus a guard grant per ref (`grantProtected`) only when `by == byUser` and the policy is protected or destructive; `checkWatches` after the agent's next turn confirms the ref (local or `origin/`) moved, or alerts. `gitRules`/`plannerGitRules` are the briefings' git rules.
- Plan pull requests (`planpr.go`, `[planner] pull_requests`, default on): after a passing test run, or a clean merge without a test command, `publishPlan` pushes the plan branch to origin with the guard env (`m.prHooks.push`, `git.Push`; never a protected branch) and opens a pull request into `planBase` with `gh pr create` unless `gh.Open` finds one; `onPlanPR` saves the URL in `Merge.PR` and posts in the plan chat (alerting the user that it is ready for review), or posts the commands to run by hand. With pull requests on, the planner's `reviewAsk` points it at the PR rather than plan chat feedback and `waitForFeedback` stays quiet. The clock's `pollReviews` reads each orchestrated plan's PR every `reviewEvery` through `m.prHooks.review` (`gh.ReadReview`: `gh pr view --json` for state, reviews and comments, `gh api …/pulls/N/comments` for line comments); `onReview` closes the plan when the PR is merged or closed, and queues reviews and comments not yet in `Merge.Seen` as an urgent `orchReview` item for the planner. Tests stub `m.prHooks` in `noAgents`.
- `plan.Plan` is the planner's output: tasks (branch, brief, optional group) and groups. Status goes `Draft` → `Running` → (`Review`, watched plans only) → `Done`. The planner writes a ```` ```grove-plan ```` JSON block that `plan.FromReply` turns into a draft; `Tidy` ungroups groups of one; `Validate` lists problems to fix before starting. Plans are saved as `plans/<id>.json`.

### internal/gitguard: git's own backstop for protected branches

- `Install(storeDir, commonDir, protected)` writes `Guard.Dir` (`<store>/hooks`): a `reference-transaction` and a `pre-push` hook, which run `<grove> git-guard <hook> --dir <Dir>` (`gitguard.Hook`, dispatched first thing in `main.go`), and `guard.json` (protected names or `path.Match` globs, the original hooks folder, the hook files written). Every hook in the user's own hooks folder (`core.hooksPath` from their config, else `<commonDir>/hooks`; `*.sample` skipped) gets a forwarding stub; the two guard hooks run the user's hook of the same name after their check passes, with the input kept in a `mktemp` file. Files are rewritten only when their content changes and stubs for removed hooks are deleted, so calling `Install` again is cheap. Scripts are `sh` with LF endings and forward-slash paths, which Git for Windows runs too.
- Nothing in any git config changes: `Guard.Env()` sets `core.hooksPath` through `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n`, numbered after any already in the environment. Append it after `os.Environ()` for processes grove starts for agents; the user's own git never sees the guard. git drops `GIT_CONFIG_COUNT` for local-transport subprocesses, so a bare remote's receive-pack is not guarded.
- `reference-transaction` checks only the `prepared` state: any update, creation or deletion of a protected `refs/heads/…` or of `ProbeRef` (`refs/grove/guard-probe`) is refused with `grove: <ref> is protected; ask the user to approve this in grove`. `pre-push` refuses protected remote branches, any deletion, and non-fast-forward pushes when the remote sha is known locally.
- `Guard.Grant(ref, worktree, ttl)` adds a one-time grant to `grants.json` (under `grants.lock`, `internal/fslock`); `worktree` "" matches any, and for pushes `ref` is the remote branch. A hook consumes one grant per guarded ref, all or none, matching the worktree from `git rev-parse --show-toplevel`; expired grants are dropped.
- `Verify(ctx, g, worktree)` needs git 2.31 (2.28 for reference-transaction, 2.31 for `GIT_CONFIG_COUNT`) and expects `git update-ref ProbeRef HEAD` under `Env` to be refused; if it went through it deletes the probe and reports the guard inactive.
- Tests use the test binary as grove (`TestMain` handles `git-guard`). `git push --no-verify` skips `pre-push`, and `git -c core.hooksPath=…` overrides the guard; those are for command classification to catch.

### internal/open and internal/config

- `open` picks per-OS implementations through `open_windows.go` / `open_darwin.go` / `open_other.go`: `ShellExecute` on Windows (falling back to the "Open with" dialog when no program is associated), `open` on macOS, `xdg-open` elsewhere. On Windows, `.ts`/`.mts`/`.cts` go to the editor instead of the system default, because Windows often maps `.ts` to video.
- `config` reads optional TOML from `os.UserConfigDir()/grove/config.toml` (`grove --init-config` writes a starter). `Git.ProtectedWith(base)` joins `[git] protected` with main, master and the base branch. `Planner.ModelFor(role, agent, ai)` gives the lead planner, group planners and task agents (`RoleLead`/`RoleCrew`/`RoleTask`) `[planner] model`/`crew_model`/`task_model`: a name `ModelAgent` ties to the other agent, or a `claude:`/`codex:` prefix for it, is skipped, and empty falls back to `[ai]`. The UI applies them in `newPlanner`, `plannerFor` and `newSession` (when `taskFor` finds a task); `/model` in a planner's chat changes only that session.

## Tests

- Releases (`.github/workflows/release.yml`) follow a CI run that passed for a push to master: `.github/scripts/next-release.sh <commit> [notes]` picks the next tag (from v0.1.0; patch by default, `[minor]`, `[major]`/`BREAKING CHANGE` in commit messages) and writes notes from the commit subjects, and `gh release create` tags that commit. Run the script locally to preview the next release.
- CI (`.github/workflows/ci.yml`) runs build, vet and `go test ./... -count=1` on Windows, Linux and macOS for every push to master and every pull request into it, plus a gofmt check on Linux. Keep tests passing on Windows: paths, line endings and what counts as an absolute path differ there.

- UI tests drive the model directly with no terminal: `fakeModel` builds a hand-made `Snapshot`, `press()` sends keys, and `plain()` renders with ANSI stripped. `TestRenderFitsScreen` checks every screen at several sizes; add new overlays or screens to it.
- Git tests build real temporary repositories (`testRepo`: main plus `feature/a` and `feature/b` worktrees that both touch `shared.txt`) and skip if git is missing.

## Gotchas

- Write Go source with the Write/Edit tools, not shell heredocs. Bash in this environment turns `\x00` and `\n` inside heredoc text into real NUL bytes and newlines, which corrupts Go string literals.
- Commit messages in this repo have no `Co-Authored-By` trailer.
